# Spec-Driven Development × Coding Agent — 普通話旁白稿


## 1. Spec-Driven Development

- `00:00:00` 歡迎收看。這一集講 Spec-Driven Development，中文可以叫「規格驅動開發」。
- `00:00:07` 目標很實際：怎樣用一份規格，讓 coding agent 寫出你真正想要的程式碼。

## 2. Vibe coding：一句 prompt 就開工

- `00:00:14` 很多人用 AI 寫程式的方式是：打一句提示詞，等它寫，不對就再改提示詞，也就是所謂的 vibe coding。
- `00:00:25` 問題一：需求很模糊，agent 只好自己猜，猜錯了你也未必馬上發現。
- `00:00:33` 問題二：它可能一次改了十幾個檔案，你很難判斷哪些改動是真正需要的。
- `00:00:40` 問題三：上下文會遺失。開一個新的 session，之前討論過的決定全部要重新講。
- `00:00:48` 問題四：沒有 review 標準，最後變成「看起來沒問題」就合併。

## 3. 咩係 Spec-Driven Development？

- `00:00:55` Spec-Driven Development 的核心只有一句話：規格是唯一的真相來源，程式碼只是規格的產物。
- `00:01:04` 也就是說，寫程式之前，先用文字講清楚要做什麼、怎樣才算完成。
- `00:01:11` 這份規格是 markdown 檔案，放在 repo 裡，和程式碼一起 commit、一起 review。
- `00:01:19` 之後需求有變，不是直接叫 agent 改程式碼，而是先改規格，再由規格推導到程式碼。

## 4. 五步流程

- `00:01:28` 整個流程可以分成五步。
- `00:01:31` 第一步 Specify：講清楚要做什麼、為什麼要做，不談技術細節。
- `00:01:38` 第二步 Plan：決定技術上怎麼做，要改哪些檔案、有什麼風險。
- `00:01:44` 第三步 Tasks：把 plan 拆成小的、獨立的、可以驗證的任務。
- `00:01:50` 第四步 Implement：讓 agent 一次只做一個任務。
- `00:01:55` 第五步 Verify：用規格裡的驗收條件檢查結果。每一步完成後，都要有人 review 才進入下一步。

## 5. 點解同 Coding Agent 特別夾？

- `00:02:04` 為什麼這個方法特別適合 coding agent？
- `00:02:08` 第一，agent 寫程式很快，但它不會讀心。規格就是把你腦中的意圖寫下來。
- `00:02:15` 第二，agent 的上下文有限，session 會結束、會被壓縮。規格是隨時可以重新讀取的長期記憶。
- `00:02:25` 第三，每一步都有文件，在只需要改規格、成本還很低的階段就能發現問題，不用等程式寫完才知道。
- `00:02:35` 第四，任務拆得夠獨立，就可以同時開好幾個 agent 並行處理。

## 6. 例子：天氣地圖加「°C / °F 切換」

- `00:02:42` 我們用一個真實專案做例子：一個用 React 和 Zustand 寫的天氣地圖。
- `00:02:49` 現在溫度全部寫死成攝氏，資訊面板和圖例都是攝氏度。
- `00:02:55` 新功能：讓使用者自己選擇攝氏度或華氏度。我們跟著五個步驟走一遍。

## 7. specs/temp-unit/spec.md

- `00:03:02` 第一步 Specify。在 specs 資料夾建立一個 spec.md，先寫一句清楚的目標。
- `00:03:11` 接著寫 user story：誰想要、想要什麼、為什麼。注意，這裡完全不談技術。
- `00:03:19` 最重要的是驗收條件。用 Given、When、Then 的格式寫，每一條都要可以測試。
- `00:03:26` 還要寫非目標，講明這次不做什麼，防止 agent 自作主張擴大範圍。
- `00:03:33` 你可以讓 agent 幫你起草規格，但一定要自己逐條看過、改過。這份就是你和 agent 之間的合約。

## 8. specs/temp-unit/plan.md

- `00:03:43` 第二步 Plan。有了規格，就讓 agent 讀程式碼，產出一份技術方案。用 Claude Code 可以切換到 Plan mode，它只會讀、不會改。
- `00:03:54` 方案要貼合現有架構：狀態放在 Zustand store，用 localStorage 記住選擇，對應 AC3。
- `00:04:03` 換算邏輯集中在一個工具函式，對應 AC4，不要分散在每個元件裡。
- `00:04:11` 列清楚要改哪幾個檔案。改動範圍一目了然，review 就容易很多。
- `00:04:17` 還要寫下風險：色階繼續用攝氏計算，只改顯示，避免影響其他圖層。

## 9. specs/temp-unit/tasks.md

- `00:04:25` 第三步 Tasks。把 plan 拆成一張 checklist。
- `00:04:30` 每個任務要夠小，小到一個 commit 就能完成，而且完成之後可以驗證。
- `00:04:37` 每個任務標明對應哪一條驗收條件，這樣每一行程式碼都能追溯回規格。
- `00:04:44` T1 和 T2 沒有互相依賴，甚至可以開兩個 agent 同時做。

## 10. Terminal

- `00:04:50` 第四步 Implement。提示詞要講清楚四件事：讀哪幾份文件、做哪一個任務、做完怎麼檢查、什麼時候停。
- `00:05:01` Agent 會先讀規格和 plan，再只修改 plan 列明的檔案。
- `00:05:06` 它自己執行型別檢查和 lint 檢查，通過之後才會勾選任務。
- `00:05:13` 最後停下來等你 review。看 diff 的時候，你只需要問一個問題：這個改動符合規格嗎？
- `00:05:21` 沒問題就 commit，再讓它做 T2。一個任務、一個 commit、一次 review。

## 11. 驗證：對返 spec，唔係對感覺

- `00:05:28` 第五步 Verify。所有任務完成後，不要憑感覺說「應該可以」。
- `00:05:34` 拿出規格逐條勾選驗收條件，每一條都要有證據，例如截圖或測試結果。
- `00:05:42` 最好把驗收條件寫成自動化測試，之後每次改程式都會自動再驗證一次。
- `00:05:49` 還可以開一個全新的 agent session 當 reviewer，讓它對照規格檢查整個 PR，它沒有之前的偏見。
- `00:05:58` 如果驗收時發現規格本身有漏洞，記住：先改規格，再改程式碼。

## 12. 放入 repo

- `00:06:05` 實際放進 repo 是這樣：每個功能一個 specs 資料夾，裡面三份文件。
- `00:06:13` 再在 CLAUDE.md 寫下規則。Claude Code 每次開啟 session 都會自動讀取這個檔案，agent 就會每次都遵循同一套流程。
- `00:06:24` 最後一條很重要：規格和程式碼有衝突時，讓 agent 停下來問人，不要自己猜。

## 13. 現成工具

- `00:06:32` 不想從零開始，也有現成的工具。
- `00:06:36` GitHub 開源的 Spec Kit 提供一套 slash command，從 specify、plan、tasks 一路到 implement。
- `00:06:45` Kiro 內建規格模式，會產生 requirements、design 和 tasks 三份文件。
- `00:06:52` 用 Claude Code 的話，Plan mode 加上 CLAUDE.md，再把常用提示詞放進 .claude/commands 做成 slash command，就已經很夠用。

## 14. 常見陷阱

- `00:07:03` 最後講幾個常見陷阱。
- `00:07:06` 一：把規格寫成技術文件。規格講要什麼，技術細節留在 plan。
- `00:07:12` 二：驗收條件太模糊，例如「要快」、「要好用」。要改成可以量測的條件，例如「一秒內更新」。
- `00:07:22` 三：一次讓 agent 做完所有任務。改動太大，你根本無法 review。
- `00:07:28` 四：程式碼改了但規格沒有跟著更新，規格很快就會變成廢紙。
- `00:07:35` 五：過度使用。改一個錯字都寫規格就太重了，小修小補直接下提示詞就好。

## 15. 重點總結

- `00:07:43` 總結一下。
- `00:07:45` 先寫規格，再寫程式；驗收條件一定要可以測試。
- `00:07:51` Plan 要貼合現有架構；一個任務、一個 commit、一次 review。
- `00:07:57` 需求有變，永遠先改規格。
- `00:08:00` 你不再是逐行敲程式碼的人，而是寫規格、做決策、把關品質的人。感謝收看！
